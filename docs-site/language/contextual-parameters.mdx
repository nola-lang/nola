A parameter written with one leading dot is a **contextual parameter**: its name, type and run-time value are composed into the prompt of every `ask` in that invocation. A plain parameter is an ordinary argument — the model sees its name in the function's signature and that no value is available; never its type or value.

## What the model sees

| Parameter | In the prompt |
| --- | --- |
| `.issue: Issue` (contextual) | name, type **and value** |
| `fallback: string` (plain) | name only, marked `(value not available)` |

```tsi
// classify-issue.tsi
export type Issue = { id: string; description: string };

// `issue` is visible to the model; `fallback` is a normal JS value only.
export infer function classifyIssue(.issue: Issue, fallback: string) {
  const kind = ask `the kind of this issue`<string>;
  return kind || fallback;
}
```

The mnemonic is *one dot in, `ask` out*: `.name` sends a value into the model, `` ask `instruction` `` brings one out (spelled `` ..`instruction` `` where `ask` is not directly in front of it — see [Extractors](/docs/language/extractors/#two-spellings-one-construct)).

## Several compose into one block

Any number of contextual parameters is fine; they compose into one context block that every `ask` in the invocation shares:

```tsi
// research.tsi
export infer function nextQuery(.question: string, .notes: string[]) {
  return ask `the single best search query to advance the research`<string>;
}
```

## Derivable types

Because a contextual value is serialized into the prompt, its type must be *derivable* to an inference schema — the same rule extractors follow: whatever the TypeScript checker resolves to a JSON-shaped structure, including unions, `Partial<T>`, `interface … extends`, `Record<string, T>` and types from packages. The full table lives on [Schema derivation](/docs/reference/schema-derivation/).

`Map`, `Set`, `Promise`, `RegExp`, functions and a generic type used without arguments are not derivable. Under the default policy a contextual parameter with such a type is a compile error, [`NOLA2008`](/docs/reference/error-codes/#nola2008).

## When a type is not derivable

Three ways out, in order of preference:

```tsi
// top-label.tsi
// 1. Pass a JSON-shaped view as the contextual parameter.
export infer function topLabel(.index: { label: string; count: number }[]) {
  return ask `the label with the highest count`<string>;
}

// 2. Keep the exotic value, but as a PLAIN parameter — the model never sees
//    its value, so nothing needs deriving.
export infer function topLabelFrom(.summary: string, index: Map<string, number>) {
  const label = ask `the label with the highest count`<string>;
  return { label, count: index.get(label) ?? 0 };
}
```

3. Relax the policy in `nola.config.ts`: `"prune"` drops just the underivable members and keeps the rest of the type; `"omit"` drops the whole type silently.

```ts
// nola.config.ts
import { openai } from "@nola-lang/providers";
import { defineConfig } from "@nola-lang/runtime";

export default defineConfig({
  model: openai({ model: "gpt-5-mini" }),
  compiler: { underivableContextType: "prune" },   // "error" (default) | "prune" | "omit"
});
```

Keep that value a literal — the editor reads it statically and cannot execute your config, so a computed value is invisible to it.

## Contextual bindings

The same dot works on a `const` or `let` **inside a body** — an infer function's or the module's. A contextual binding is context for every `ask` that comes after it in the same body, in its block or an enclosing one:

```tsi
// support.tsi
type Customer = { id: string; tier: "free" | "pro" };

export infer function reply(.mail: string) {
  const .tone = "brief, friendly";
  const .customer: Customer = { id: "c1", tier: "pro" };
  return ask `a reply to the mail`<string>;
}
```

- The binding renders after the parameters in the function's `CONTEXT` block — `- tone = "brief, friendly"` — and its **current** value is read when the ask runs, so a reassigned `let .x` contributes what it holds at that moment.
- Visibility is lexical: an ask sees the bindings declared before it, in its block or an enclosing block of the same body. `const .bio = ask …` never lists itself, and nothing declared after an ask reaches it.
- An annotated binding (`const .customer: Customer`) derives its type exactly as a contextual parameter does, under the same `underivableContextType` policy; an unannotated one carries the value alone.
- `ask fn()` hands the bindings visible at the call site to `fn` as its caller's context, the way parameters already travel.
- At module level the bindings give the implicit `<module>` scope its `CONTEXT` block — see [ask at module level](/docs/language/ask/#at-module-level). They do **not** reach an infer function merely declared in the same file; context chains where `ask` happens.
- `var .x` is not a binding form ([`NOLA1014`](/docs/reference/error-codes/#nola1014)); a pattern after the dot is [`NOLA1011`](/docs/reference/error-codes/#nola1011); a dotted binding inside a plain function is [`NOLA1010`](/docs/reference/error-codes/#nola1010).

## Errors

- [`NOLA1010`](/docs/reference/error-codes/#nola1010) — `.` on a parameter of a plain (non-infer) function, or on a binding outside an infer body / the module body. Drop the dot; it is an ordinary argument or variable.
- [`NOLA1013`](/docs/reference/error-codes/#nola1013) — `..name`: contextual parameters take one dot; two dots is the extractor sigil.
- [`NOLA1012`](/docs/reference/error-codes/#nola1012) — an incomplete `.` with no name after it.
- [`NOLA1011`](/docs/reference/error-codes/#nola1011) — `.` on a destructuring pattern or a parameter with a default value; reserved — use a plain identifier parameter.
- [`NOLA1014`](/docs/reference/error-codes/#nola1014) — `var .x`: a contextual binding is `const .x` or `let .x`.
