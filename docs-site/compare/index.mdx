Nola adds model calls to TypeScript through `.tsi` files, typed `ask` expressions, and contextual parameters. Other tools solve similar problems through generated clients, library calls, or workflow graphs.

The pages in this section use the same small task: classify a support message, then write a reply using its category. They compare how you organize code and types. They do not measure model quality, latency, or cost.

For Nola's design goals, see [Why Nola](/docs/start/why-nola/). For complete projects, the repository also includes an [inbox-triage comparison](https://github.com/nola-lang/nola/tree/main/comparisons/inbox-triage). That comparison uses a different task involving extraction and function calling.

## The matrix

These are the approaches used in the examples, rather than an exhaustive list of each tool's capabilities.

| | Nola | BAML | Vercel AI SDK | LangGraph (JS) |
| --- | --- | --- | --- | --- |
| **What it is** | A TypeScript superset | A language for LLM functions | A TypeScript library | A workflow orchestration library |
| **Where the output shape lives** | A TypeScript type | A BAML class | A Zod schema | A Zod schema passed to the model integration |
| **How callers get types** | Nola's compiler and editor support | Generated client types | Types inferred from the schema | Types inferred from state and output schemas |
| **How the two steps connect** | Two asks in one infer function | TypeScript calls two generated functions | Two library calls | Two nodes connected by an edge |
| **Context in the example** | A contextual parameter shared by the asks | Arguments passed to each function | Inputs passed to each call | Data read from graph state |
| **Tooling to adopt** | Nola compiler, loader or build plugin, and editor extension | BAML generator and optional editor extension | SDK and provider packages | Graph library and model integration |

BAML's [prompting guide](https://docs.boundaryml.com/guide/baml-basics/prompting-with-baml), the AI SDK's [Output reference](https://ai-sdk.dev/docs/reference/ai-sdk-core/output), and the [LangGraph overview](https://docs.langchain.com/oss/javascript/langgraph/overview) describe the corresponding APIs.

All four can work with typed results. The distinction is how the schema is defined and connected to application code. Nola derives its schema during compilation; the response is still validated at runtime. With a schema library such as Zod, the schema can be the source of truth for the TypeScript type, without maintaining a second declaration.

## Reading the rest

- [Nola vs BAML](/docs/compare/baml/) compares TypeScript types and shared function context with BAML definitions and generated clients.
- [Nola vs LangGraph](/docs/compare/langgraph/) compares a short sequence of asks with a graph, then explains how to combine them.

Two related Python tools address different concerns. [DSPy](https://github.com/stanfordnlp/dspy) provides modules and algorithms for optimizing prompts and model weights. [LMQL](https://lmql.ai/docs/language/reference.html) combines Python control flow with query strings and [generation constraints](https://lmql.ai/docs/latest/language/constraints.html). Neither has a detailed comparison page here.
